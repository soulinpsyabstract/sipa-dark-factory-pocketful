The defect this wave closed (sec F)
  Five of the seven write paths fingerprinted body.model_dump(mode="json")
  instead of the request. Every request schema is extra="ignore", so
  unrecognised fields were dropped before hashing and two different bodies
  could collide into one fingerprint, producing a silent replay where the
  spec owes a divergence error. Same defect class as the W5 import
  double-spend: fingerprinting a normalised projection rather than the
  request itself.

  Money was never at risk. A replay returns the original response and moves
  nothing, so the observable damage was a masked client bug, not a double
  spend. Recorded plainly rather than overstated.

  Proven on 980c679f1f76 BEFORE the fix, same key, four bodies:
    {to,amount:10}         -> 200 pay_1
    + extra:'surprise'     -> 200 pay_1     <-- different body, silent replay
    + note:'different'     -> 409 idempotency_key_reuse
    amount:999             -> 409 idempotency_key_reuse
    ada 2000 -> 1990, bob 0 -> 10         (money moved exactly once)

  Same probe on 15b06fff3b7c AFTER the fix:
    {to,amount:10}         -> 200
    identical replay       -> 200 (replays, unchanged response)
    + extra:'surprise'     -> 409           <-- fixed
    amount:999             -> 409

Stronger guarantees found and pinned while writing them
  - capture refuses unknown fields outright, 422 validation_failed, before
    idempotency is consulted; it does not merely fingerprint them differently
  - an absent or blank body normalises to b"{}", so genuine no-body retries
    still replay; but on a body-required path a whitespace body fails JSON
    decoding and is refused 422 rather than read as absent
  - an identical replay still returns the original status and body
  - keys remain scoped per user across paths
