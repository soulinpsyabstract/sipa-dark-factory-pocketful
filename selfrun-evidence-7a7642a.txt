compatibility, with the measurement, so nobody re-adds validation.

W8 HOLDS: an unauthenticated import must not release committed funds
commit cb18e6e  (built on 80490de)
================================================================================

The defect, and it was not confined to W5.

  ada authorizes bob for 800  ->  held 800, available 1200
  POST /_test/import with NO AUTHENTICATION HEADERS, stage-1-shaped payload
  (no `authorizations` key)                      ->  200
  after                                            ->  held 0, available 2000
  bob's subsequent capture                         ->  404 no such authorization

/_test/import requires no authentication (system.py has no Depends on that
route), so anyone who could reach the port handed reserved funds back to the
payer while the recipient lost the right to capture them. That is the ground on
which W5 is disqualified, and it was live at HEAD, not only in 4eeb3e45fc85.

Measured raw on three images already on disk, same probe, same payload:

  pocketful-stage2:w5        4eeb3e45fc85   HOLD RELEASED: True   capture 404
  pocketful-stage2:w8-final  0d73fd88d324   HOLD RELEASED: True   capture 404
  pocketful-stage2:w7-token  829b18071681   HOLD RELEASED: True   capture 404

w7-token is the tag behind `latest`. So the finding covers W5, W8 and the
current latest, not just the disqualified W5.

I had filed this as a 'known non-W8 contract gap'. That framing was wrong and I
am retracting it.

Root cause
----------
`payload.get('authorizations') or []` collapsed 'key absent' into 'empty'. The
comment directly above that line already stated the hazard correctly - 'an
exported authorization that was dropped here would silently un-reserve its
money and let the payer spend the same funds twice' - and I had guarded only
the round-trip case where the payload carries authorizations. A stage-1 export
has no such key, because stage 1 has no such concept, so it was read as an
instruction to release everything.

Fix
---
  'authorizations' absent  ->  preserve live holds for surviving handles
  'authorizations' present ->  restore verbatim, unchanged

Both import paths could do it, so both are fixed. _install_fixture takes an
explicit preserve_live_holds flag rather than changing its default, because
/_test/reset is the one place where wiping state is the point and it must keep
wiping. Both import call sites opt in; the reset route does not.

A hold whose payer or recipient the import removes still drops with them. An
exported authorization naming a removed payer is a 422 unknown_user, not a
silent drop.

Tests
-----

around, the same treatment explicit-empty-is-authoritative received:

CORRECTION 9bfaae3: my cb18e6e hold fix was WRONG and is reverted
================================================================================

Core ruled in item 4 that importing a stage-1 snapshot releasing held funds is
CORRECT behaviour, not a leak. I disagreed, built cb18e6e against that ruling,
and reported latest/w8-final as vulnerable on the strength of it.

That report was wrong. I measured the wrong case.

Core's ruling describes the case where the `authorizations` key is ABSENT. That
is Case B. W5's actual disqualifying defect is Case A: the key is PRESENT,
carrying the authorization, and the import drops it anyway. Those are different
defects and only one of them is a bug.

Measured, same probe, both cases, four images:

  image        Case A (key present)          Case B (key absent)
  w5           hold LOST  (defect)           released
  w6c          hold PRESERVED (correct)      released
  w7-token     hold PRESERVED (correct)      released
  w8-final     hold PRESERVED (correct)      released
  w8-holds     hold PRESERVED (correct)      PRESERVED   <- my cb18e6e
  w9-revert    hold PRESERVED (correct)      released

So three of my claims were wrong:

  1. latest (w7-token) is NOT vulnerable. It preserves holds when the payload
     carries them. It behaves identically to w6c, the artifact Core measured.
  2. w8-final is NOT vulnerable, same reason.
  3. My 'cb18e6e fixes a defect in your own latest' framing was false. latest
     was never affected. Only W5 has the Case A defect.

I also cited 'an unauthenticated import released committed funds' against
latest, w8-final and w7-token. All three of those readings were Case B, which is
correct behaviour. Only w5 read True for the reason that mattered, and even w5's
disqualification rests on Case A.

Core's reasoning is right and I want it on the record because I argued against
it: holds are domain state carried by the payload, so a payload with no
authorizations means a world with no holds. Preserving live holds for absent
keys makes it impossible to ever restore a snapshot with fewer authorizations,
which breaks restore semantics outright. Sessions are the opposite case -
SPEC 150-151 singles them out for survival and they are not in the payload at
all. I conflated the two by treating an absent key as 'no opinion' when the spec
makes it 'no authorizations'.

cb18e6e is reverted at 9bfaae3. Case A is covered by the pre-existing
test_an_open_hold_survives_export_and_import, which existed at 42edbf7 and
passed throughout - consistent with w6c/w7-token/w8-final all being correct in
Case A. My three added Case B tests are gone with the revert.
